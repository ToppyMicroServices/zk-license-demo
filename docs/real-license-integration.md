# 実免許証連携の利用条件調査

更新日: 2026-10-16（初回調査: 2026-10-15）。公開一次資料の調査であり、利用申請、契約、問い合わせ送信、
実カードの読み取り、実サービス接続は行っていない。

## 読み取りと署名

警察庁の[仕様書（2024-07-19通達）](https://www.npa.go.jp/laws/notification/koutuu/menkyo/menkyo20240719_145.pdf)
には、従来のIC免許証とマイナ免許証の記録形式・読出しコマンド・署名処理がある。
従来の免許証ではDF1/EF01、DF1/EF02、DF2/EF01を署名対象にしている
（PDF 17ページ、本文2-11）。この署名対象を、追記情報を含む全データと解釈しない。
マイナ免許証には別の記録形式がある（PDF 34ページ、本文3-6）。
実装時は対象の版と署名対象バイト列を固定し、正規の試験データで照合する。
このrepoのAnonCreds署名は、これらの公的署名とは別物である。

従来の免許証の真正性検証について、SDK提供元の
[LibJeID検証ガイド](https://www.osstech.co.jp/download/libjeid/validation-guide/)は
PIN1とPIN2の両方を必要としている。署名値の検証に加え、使用した証明書の信頼性を確認する設計を説明している。
カードから読めた値だけで、発行者を信頼したことにはしない。

マイナ免許証の[公式スマートフォン版マニュアル](https://myna-menkyo-app.npa.go.jp/manual/manual_sp.pdf)
（7–8ページ）は専用の4桁暗証番号と、暗証番号を設定していない場合の操作を案内する。
氏名等をあわせて表示する操作は追加の入力がある。従来のPIN1/PIN2手順をそのまま流用しない。
同マニュアル11ページには、真正性検証用の電子証明書が更新された場合のダウンロード操作もある。

## ソフトウェア利用と公開鍵

公式アプリの[利用規約](https://myna-menkyo-app.npa.go.jp/terms.html)第1項は、保有者と、
保有者の免許情報を確認する必要がある者を利用目的に含める。
ただし第5・7項はアプリやその著作物の無断複製・改変等を制限している。
公式アプリの利用条件を、自作アプリへの組み込み・鍵ファイルの再配布の許諾と扱わない。
本文はページが読み込む[公開XML](https://myna-menkyo-app.npa.go.jp/data/xml/terms.xml)も直接確認した。

[LibJeID製品ページ](https://www.osstech.co.jp/product/libjeid/)では、免許証の署名検証は有償版の機能で、
年間契約・個別見積もりとされている。無償版にも表示義務や再配布・流用の制限がある。
「無償だから公開repoに同梱できる」とは判断しない。
[製品版の導入手順](https://www.osstech.co.jp/download/libjeid/android/full/)も、
配布物の取得にサブスクリプションIDとアクセスキーが必要としている。
今回はSDKを追加していない。

### 追加確認: 取得・更新経路と利用契約

[LibJeID Androidの更新履歴](https://www.osstech.co.jp/download/libjeid/android/release/)には、
2023-02-17の47都道府県の証明書更新、2023-04-06の警察庁提供の不備修正版への差し替え、
2024-10-10の32都道府県の証明書更新が記録されている。
2025-10-31にはマイナ免許証の読み取り・真正性検証への対応も記載されている。
ベンダー経由で証明書を更新する実例は確認できた。更新頻度の保証、旧鍵の保持、
契約終了後の使用権、鍵だけを取り出す権利までは、この履歴からは確認できない。

NTTデータの[2010年のBizPICO発表](https://www.nttdata.com/global/ja/news/release/2010/092700/)も、
公安委員会の公開鍵を警察機関から一括取得し、随時更新・保管する仕組みを説明する。
これは過去の提供例である。[現在の商品ページ](https://www.nttdata.com/jp/ja/lineup/bizpico-mint/)は
JPKIを中心に説明しており、同じ免許証向け機能が現在も同条件で契約できるとは判断しない。

[デジタル庁の民間向け資料 Vol.91](https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/33a0798a-be04-4ec5-b50a-f2a784755a05/c58da91e/20250829_policies_mynumber_private-business_infomation_02.pdf)
（2025-08-29、PDF 5ページ）は、民間ライブラリで読んだ免許データと真正性確認データを
提供事業者へ送って検証する構成を示し、iTrustを例示する。
これは民間連携の構成例であり、公開鍵の自由配布や停止・取消し照会の許諾ではない。
[iTrust提供元](https://www.cybertrust.co.jp/pressrelease/2025/0218-mynumber-itrust.html)も、
マイナ免許証の読み取り・署名検証ライブラリの提供を公表している。

[iTrust公開約款 v1.5.12](https://www.cybertrust.ne.jp/itrust/repository/iTrustIdentificationService_Terms_v1.5.12.pdf)
（2026-04-20発効）の第3・4条は、申込みと所定手続、API接続用証明書等の交付を定める。
第3条2項では、ライブラリによる情報取得は原則として同社APIの検証機能と併用し、
取得だけの利用には事前の書面合意が必要とされる。利用者への提供許諾と一般配布は区別されている。
ただし、この約款の定義はJPKIを中心としているため、免許証機能に適用される契約一式・特約は
提供元への確認が残る。公開約款だけで本repoへのSDK同梱を許可されたとは扱わない。

**未確認:** 従来の免許証・マイナ免許証それぞれについて、自作サービスで利用できる
信頼済み公開鍵一式の正式な取得先、利用・再配布範囲、真正性を確認する基点、更新通知、
旧鍵の保持期間と事故時の失効手順。公式アプリの更新機能があることは確認できたが、
その配布口を第三者サービス向けの公開APIと認定できる資料は確認できていない。
SDK採用の場合も、鍵の提供・更新責任と対象OSを契約・現行仕様で確認する必要がある。
これは現在の調査範囲での未確認であり、提供制度が存在しないという結論ではない。

## 停止・取消し・失効の照会

署名検証が示すのは、署名対象データと発行元に関する事実である。
カードの記録された有効期限との比較だけでは、その後の免許停止・取消しを確認できない。
デモの結果には `live_licence_status_checked: false` を明示する。

自動車安全運転センターの[申請方法](https://www.jsdc.or.jp/certificate/tabid/110/Default.aspx)では、
オンライン申請は本人に限り、NFC対応端末とPIN1等を要する。
証明は郵送で、入金確認後通常10日程度とされ、直前の違反が記録されていない場合もある。
別途、委任による窓口申請や企業一括申請の案内はある。
これらは、サービスが即時に呼べる現況照会APIを確認した証拠にはならない。

[企業一括申請の現行案内](https://www.jsdc.or.jp/certificate/tabid/196/Default.aspx)は、
運転記録証明書と無事故・無違反証明書を対象とする。通常は委任状が必要だが、
申請者を特定できるグループウェアで委任意思を確認する方式もある。
後者は申請書、回答結果、誓約書を指定ストレージへ提出し、事前に事務所と確認する手続である。
これは従業員の安全運転管理向けの申請経路であり、任意の顧客を無条件に照会するAPIではない。
一般の[窓口・郵送申請](https://www.jsdc.or.jp/Default.aspx?TabId=110&vm=r)も即時交付ではなく、
郵送は申請から1〜2週間程度とされている。オンライン本人申請の「入金確認後約10日」と起点が異なる。

警察庁の[2025-03-10通達](https://www.npa.go.jp/laws/notification/menkyo20250310_111.pdf)
（PDF 6ページ、2(3)ア）は、取消し・失効・効力停止等の場合、保有者が公安委員会へ
マイナ免許証を提示して免許情報記録の抹消を受ける運用を説明している。
ここから、手元のIC記録が処分情報と常時自動同期されるとは判断できない。
署名が正しい古い読出し結果を、現在も運転可能である証拠にしない。

**未確認:** 一般の民間サービスが利用可能な最新状態照会の提供主体、対象資格、申請条件、
API仕様、反映遅延、照会同意・目的制限、料金、停止時の扱い。
実連携前に窓口または契約先から根拠を得る。問い合わせは未送信。
状態不明を「有効」に変換しない。アプリ側の資格情報失効機能を実装しても、
警察側の処分を知る情報源は別途必要である。

次の確認事項はBeads `zkl-boe` と `zkl-s6a` に残す。
鍵の提供元には、対象カード、信頼基点、更新通知と反映期限、不備・漏えい時の差し替え、
旧鍵保持、サーバー利用・再配布・契約終了時の権利を確認する。
状態情報の提供元には、民間サービスの利用資格、本人同意と照会目的、返却する状態の定義、
処分の反映遅延、照会時刻、料金、障害時の扱いを確認する。
契約条件が確定するまでは、模擬実装の `live_licence_status_checked: false` を維持する。

## 実ユーザー認証と進め方

[デジタル庁のJPKI案内](https://www.digital.go.jp/policies/mynumber/private-business/jpki-introduction)
は、自ら認定を受ける方式と、認定された事業者へ署名検証業務を委託する方式を説明している。
自ら行う場合の技術仕様取得にはJ-LISとの守秘義務に関する誓約・開示申請がある。
JPKIの電子証明書の有効性と、運転免許の現在の有効性は異なる。
Passkeyは登録した認証器の利用を確認するもので、実名との初期の結び付けは別途設計する。
参照: [W3C WebAuthn](https://www.w3.org/TR/webauthn-3/)。

推奨する次の段階は、信頼できる発行側で実カードを読み取り・検証した後、必要な属性だけの
資格情報を発行し、保有者側で同意と証明を行う構成の検討である。
現在のローカル版は全役割を同一プロセスに置いた模擬実装であり、この分離は未実装。
直接、公的なRSA署名の検証までZK内で行う方式を実装済みとは扱わない。

| Beads | 作業と次に必要な証拠 |
| --- | --- |
| `zkl-45z` | 初期の公開資料調査。利用条件と未確認事項を本書に記録 |
| `zkl-boe` | 正式な公開鍵取得・利用・更新条件。配布元または契約資料で確認 |
| `zkl-s6a` | 最新状態照会。利用可能な提供元・申請資格・鮮度の確認 |
| `zkl-d2q` | 実カード読出し・署名検証。上記条件と許可された試験資料に依存 |
| `zkl-69f` | 実本人確認とPasskey連携。提供者、登録、復旧、保有者への結び付け |
| `zkl-e14` | ウォレットの分離と保有者側の秘密保持 |
| `zkl-88t` | 発行鍵の更新・失効・復旧。模擬資格情報の失効対応を含む |
| `zkl-9w9` | 本番API、運用・負荷・障害復旧。模擬テストで完了としない |
